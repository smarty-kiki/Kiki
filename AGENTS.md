# Kiki - Agent Instructions

## Overview

macOS menu bar companion app. Lives entirely in the macOS status bar (no dock icon, no main window). Clicking the menu bar icon opens a custom floating panel with companion voice controls. Push-to-talk (ctrl+option) captures voice input, transcribes it on-device, and sends the transcript plus a screenshot of each display to DeepSeek. The reply is streamed and spoken on-device while it is still being written, and a blue cursor overlay can fly to and point at — or click, scroll and drag — UI elements the model references.

A second entry point into the same pipeline ships alongside it: `kiki command '…'`, a command line tool that hands a typed request to the running app over a Unix domain socket and streams the reply back to the terminal. Everything downstream of the text — teardown, capture, model, speech, pointing, acting, history — is the identical code path. The same tool's `kiki click` is the other half: one mouse gesture, no model and no voice, for scripts and shortcuts. `kiki doubleclick`, `kiki tripleclick` and `kiki rightclick` are that command pressing twice, three times or on the right button, `kiki scrollup`, `scrolldown`, `scrollleft` and `scrollright` are it rolling what is under the point by `-b` screenfuls — half a screen at the finest, for reading a long list without overshooting the part that mattered — and `kiki drag` is it pressing on one point and letting go at another, the destination given as `--to-x`/`--to-y`.

A third kind of input skips the model entirely: one tap of shift+option records what the user does with the mouse, the next ends the recording and replays it on a loop, and a third stops the replay and forgets it.

The only credential is the user's DeepSeek API key, pasted into the settings panel and stored in the macOS Keychain. Transcription, text-to-speech and screen capture all run on-device. Nothing sensitive ships in the binary and no proxy sits in front of the API.

## Architecture

- **App Type**: Menu bar-only (`LSUIElement=true`), no dock icon or main window
- **Framework**: SwiftUI (macOS native) with AppKit bridging for the menu bar panel and the cursor overlay
- **Pattern**: MVVM with `@StateObject` / `@Published` state management
- **AI Chat**: DeepSeek (`deepseek-flash` default, V4 Pro optional), called directly from the client with SSE streaming. Every chunk is consumed as it lands — the reply is cut into speech segments while it is still being written, and each one is synthesised the moment it can no longer change.
- **Speech-to-Text**: Apple's Speech framework (`SFSpeechRecognizer`), on-device. Keyterms go through as `contextualStrings` so proper nouns and on-screen UI labels bias recognition.
- **Text-to-Speech**: Apple's `AVSpeechSynthesizer`, on-device. Picks the highest-quality voice installed for the current locale; `AppleTTSVoiceIdentifier` in Info.plist pins an exact voice, because the installed-voice list is not stable between enumerations.
- **Screen Capture**: ScreenCaptureKit (macOS 14.2+), multi-monitor
- **Voice Input**: Push-to-talk via `AVAudioEngine` plus a pluggable transcription-provider layer, with a listen-only `CGEvent` tap for the system-wide shortcut.
- **Element Pointing**: The model embeds `[POINT:x,y:label:screenN]` tags in its reply — written as `[CLICK:…]`, `[DOUBLECLICK:…]`, `[TRIPLECLICK:…]`, `[RIGHTCLICK:…]`, `[SCROLLUP:…]`, `[SCROLLDOWN:…]`, `[SCROLLLEFT:…]`, `[SCROLLRIGHT:…]` or `[DRAG:x,y:label>X,Y]` when the element is one the user is meant to operate, and written inline against the words naming the element. The label names the element and the app finds that text on the picture, so the coordinate is only a hint about which occurrence was meant. A drag is the one tag with two points: the element is what gets carried and the point after `>` is where it is let go.
- **Element Acting**: A click, scroll or drag tag is an instruction to act, and the kinds meet at `ElementActionOnArrival`. A click is one axis — which button, how many presses (one, two or three), `ElementClickKind` — and a scroll is another: which direction, how many screenfuls, `ElementScrollDirection`. The two never mix, and everything downstream is read off the one value they meet in: whether the flight is a red one, which bubble is said, whether anything happens on arrival, and whether the user's pointer is taken along. A drag is neither axis: it is the one gesture whose action is a movement *between* two points rather than an event at one, so it carries its destination beside the action rather than inside it, and it is the one action still running after the cursor has landed. When the cursor arrives, Kiki posts the real event with `CGEvent` — after flying to the user's pointer, turning red, and carrying it along to the element, which is what makes "Kiki is about to press this" legible before anything is pressed. A right click goes through the same ritual and leaves the pointer sitting on the context menu it opened; a scroll carries the pointer the same way and moves the content under the point, making no sound, because the content moving is its own feedback; a drag carries the pointer every step of the way to the drop point.
- **The Turn As A Loop Of Steps**: a turn is one reply or several, and the several are what make it a loop. The model ends a reply that acts on the screen with `[LOOK]` on its own, and once every action that reply asked for has reported back, Kiki takes a fresh screenshot and asks again with a sentence saying what those actions did — so the next step reads a screen nothing else in the app has seen. One reply is still one step whatever it contains: three tags in one reply are three presses and then one report, never a round trip each. A step ends when the stream has stopped, the cursor has run out of stops, and every action has reported; the turn ends when the model stops asking to look again, when every action was refused — the screen did not change, so a second look would earn the same reply — or after `maximumStepsInTheTurnBeingAnswered` steps. The prompt reads that number off the constant rather than restating it, and it is the budget a search is spent from: a folder costs two steps to look inside, one to open it and one to come back out. **The voice is not one of the three and does not hold the next step back**: a step whose screen work is done is handed to the model at once, and only the audio queues behind the sentence still playing, so a model that runs ahead of its own narration is the ordinary case rather than a fault — the narration is one continuous run for the whole turn, a step's segments being appended to the turn's list rather than replacing it. The terminal watching a turn is sent `done` when the turn ends rather than when a step's stream does, and every snapshot it is sent is the whole turn.
- **Two Histories**: one task has two records of itself. `conversationHistory` is the full one, an entry per step, kept for the length of the task. What a request carries is the newer end of that same array, whole, with everything older compressed into `summaryOfTheStepsCompressedOutOfTheContext` — a paragraph written by the model itself under `conversationCompressionSystemPrompt`, which keeps four things: what the user asked for, what has been done, every error and dead end and why, and what is unfinished. The trigger is the estimated context reaching `fractionOfTheContextThatStartsCompression` of `contextTokenCountOfTheModel`, checked before the screenshot is taken. Both histories are cleared together after `maximumGapBetweenTurnsInTheSameConversationSeconds` without activity, because an idle gap ends the task and both are records of that task.
- **Recording and Replaying the User's Own Actions**: one tap of shift+option starts recording what the user does with the mouse, the next ends it and replays it on a loop, and a third stops the replay and forgets it. A recorded action is stored as the value the arrival performs — an `ElementActionOnArrival` beside the global point it happened at, `RecordedUserAction` — so a replay is not a second way of acting but the same one with a different answer address: it resolves its point through `resolveActionTarget`, inherits that function's refusals, flies the same red carrying flight and posts the same `CGEvent`, reaching `ElementScroller` with a distance recorded in points rather than in screenfuls. Nothing about it touches the reply, the voice, history or analytics, and a step whose point no longer resolves is skipped rather than ending the loop.
- **Command Line Tool**: ten subcommands in a separate `kiki` target. `kiki command '…'` runs the whole pipeline on a typed request; `kiki click -x/-y` or `-t/-n/-s` asks the app for one mouse click and nothing else; `kiki doubleclick`, `kiki tripleclick` and `kiki rightclick` take the same arguments and meet the same refusals, and press two, three or the right button; `kiki scrollup`, `scrolldown`, `scrollleft` and `scrollright` take those arguments plus `-b <screenfuls>`, 0.5 to 20, and roll what is under the point that far; `kiki drag` takes them plus `--to-x`/`--to-y` and carries what is under the starting point to the destination, which only coordinates can name. Unix domain socket at `~/Library/Application Support/Kiki/command.sock`, JSON Lines both ways, absolute snapshots of the reply rather than deltas. Connections are held in a table and given a role by what they *ask for* rather than by the order they arrived in: a `command` becomes the terminal watching the reply and takes that role from whoever held it, while a gesture takes no role at all and is answered on its own connection. The tool launches the app through `/usr/bin/open` when nothing is listening, and refuses with exit 2 if the app reports it cannot do what was asked.
- **State**: the panel's 等待中 / 聆听中 / 处理中 / 回复中, the cursor's four states of visiting the menu bar icon, and the recorder's recording / replaying are three facts behind one question, `whatKikiIsDoingRightNow`, and `voiceState` is derived from the facts rather than assigned, so a state no fact supports is not reachable.
- **Concurrency**: `@MainActor` isolation, async/await throughout
- **Analytics**: PostHog via `KikiAnalytics.swift`

## Rules That Bite If Broken

Agents and readers of the code cannot recover these from the source. Most of them are traps where the obvious thing is the wrong thing, or where a failure is silent.

### Platform and permissions

- **Read `Locale.preferredLanguages`, never `Locale.current`.** Anything that needs to know what language the user actually speaks must go through `Locale.preferredLanguages`. `Locale.current` and `Locale.autoupdatingCurrent` resolve against the app bundle's *own* localizations, and this bundle ships no `.lproj` at all, so inside the running app they always resolve to English — even on a Mac whose system language is Chinese. This has already produced an `en-US` recognizer on a Chinese Mac, forcing Mandarin speech into English. The failure is invisible from a command-line test binary, which has no bundle and reports the real system locale; verify by building and running the app.
- **Launch with `open`, not the binary.** Running `Kiki.app/Contents/MacOS/Kiki` from a shell has tccd answer Screen Recording for the *terminal*: the startup line then reads `screen: false` while System Settings shows the app granted, with a `授权` button that opens an already-granted row. Everything else on that line — Accessibility included — reads the app's own signed record instead and stays true on the same launch, so this is one flag and not five. Building from the terminal is safe.
- **Kiki is deliberately not a login item, and no launch may register one.** `SMAppService.mainApp.register()` cannot tell "never registered" from "turned off in System Settings", so calling it at launch silently undoes a choice the user made there. Nothing needs it: `kiki command` and the nine gestures start the app themselves through `open`, and only the push-to-talk path loses its zero-friction start after a logout. Deleting the call does not delete an existing registration — that lives in the system's background-items database and has to be removed once by hand.
- **Speech Recognition is a permission in its own right** (`kTCCServiceSpeechRecognition`), separate from the microphone. It is a row in the settings panel and must stay inside `allPermissionsGranted`, because the panel renders the setup section only while that is false — a permission left out becomes un-grantable the moment the other four are in place. It counts only when the *resolved* transcription provider actually needs it: `BuddyTranscriptionProviderFactory` silently falls back to Apple Speech when a preferred provider has no key, so read the resolved provider rather than the Info.plist preference.

### Coordinates

- **There are two global screen spaces and the flip between them lives in exactly one place.** AppKit's origin is the primary display's bottom-left with y increasing upward; `CGEvent`'s `mouseCursorPosition` and the Accessibility API use that same display's top-left with y increasing downward. So `axY = primaryScreenHeightInPoints - appKitY`, and x needs nothing. Other displays need no special case — including one *above* the primary, which this maps to a negative Accessibility y, exactly how the Accessibility API describes it. The only copy is `ElementClicker.accessibilityPoint(fromAppKitScreenLocation:primaryScreenHeightInPoints:)`, `fileprivate` so `PointerCarrier` reuses it; its inverse, `appKitScreenLocation(fromAccessibilityScreenPoint:primaryScreenHeightInPoints:)`, calls it rather than writing the subtraction a second time. A second copy puts the click a whole screen height from the cursor.
- **The model's coordinates are divided by the screenshot's pixel size, read off the encoded image — never from `configuration.width`.** Those are the same number only if ScreenCaptureKit honours the requested size, and if they disagree the model is told a coordinate space its image does not have, so the cursor lands proportionally short of the element. The failure is invisible: the label the model read and the arithmetic the app does would both describe an image that was never sent.
- **HiDPI is a legibility question here, not an offset.** Every size on the capture path is either all-points or all-pixels and the conversion between them is a pure ratio, so `backingScaleFactor` has no call site. A scale factor leaking in would not produce a slight drift; it would put the cursor at roughly double its distance from the origin.

### State

- **`voiceState` is derived from the facts, never assigned to.** `settleVoiceState()` is its only writer, onto what `voiceStateTheFactsSupport` reads off the microphone and the reply, and the guard inside it is what keeps an unchanged `@Published` write from invalidating every view reading it. The one exception is the low-credits message, which goes out through an `NSSpeechSynthesizer` of its own that reports nothing back and so is not one of the facts. The derivation is what removed the arbitration the two writing groups needed; a direct write anywhere else brings it back — a guard at every call site that has to know what the other side is doing.

### Speech

- **Never call `pauseSpeaking` or `continueSpeaking`.** A resume and a pause inside the same second leaves the synthesizer silent for the rest of the utterance *while reporting `isPaused == false`*, which defeats every release path at once — they all consult that property, and it is the thing that is lying. Neither call appears in `AppleTTSClient`, and that is what makes the whole class of failure unreachable rather than rare. The wait they were used for is expressed instead by **not handing over the next segment**: the narration waits for the cursor, and the cursor never chases the words.
- **Only one `write()` may be in flight.** `prepareSpeechSegment` has to return immediately — it is called the moment a segment's text stops changing, while the model is still writing — but a second `write()` disowns every callback the first one was still owed, including the zero-length closing buffer that is the *only* thing marking a segment complete. `speakPreparedSegment` waits on that with no deadline at all, so the reply does not fail, it never returns. `queuedSegmentsWaitingForSynthesis`, drained by that same closing buffer, is the whole reason the queue exists.
- **A segment that has been spoken through has reached its stops, words or not.** The synthesizer genuinely skips some word reports — short segments report none at all — and the words are the only thing that sends the cursor. `hasCurrentSpeechSegmentFinishedSpeaking` satisfies the trigger on its own so a stop waiting on a word that never arrives cannot hold both the cursor and the rest of the reply.
- **Transcription and text-to-speech are on-device.** They cost nothing, work offline and send no microphone audio off the machine. The provider is `VoiceTranscriptionProvider` in Info.plist; the AssemblyAI, OpenAI and ElevenLabs clients in the tree are retained as reference implementations and are unused.
- **The dictation engine is replaced, never repaired, when the audio configuration changes.** `AVAudioEngine`'s `inputNode` caches its format from the first time it binds to the hardware, so an engine built for one device goes on reporting that device's sample rate after the input device has changed — and handing the stale rate to `installTap` is not a Swift error but an Objective-C exception, which `try` cannot catch and which takes the process down when it unwinds through the concurrency frames that started the dictation. A fresh `AVAudioEngine` is the only thing that re-reads the live format, so `theAudioInputDeviceChangedUnderTheAudioEngine` rebuilds the engine whole on `.AVAudioEngineConfigurationChange`. That notification comes from the engine's I/O unit and arrives **even when the engine is not running**, so the restart is conditional on a transcription session being live rather than on the notification. The observer is scoped with `object: audioEngine`, because `AppleTTSClient` holds a second `AVAudioEngine` in the same process.

### The streaming reply

- **Every pass between the raw text and the segments must be prefix-stable.** Tidying a prefix of a reply has to give the same characters as tidying the whole reply and cutting, and the same goes for the tag parse and the sentence scan. The segmenter re-parses the whole accumulated reply on every chunk and cuts segments out of the answer; that is only sound because a segment cut from an earlier, shorter document is the same segment in the longer one. A pass that failed this shows up as a segment the voice has already been given changing its mind.
- **A numbered list marker is the known case that cannot be made prefix-stable** — a prefix cut between the `1` and the `.` is a bare `1`, which is equally the start of a marker and the start of a number. That is the entire reason nothing handles lists; the prompt asking for none is the defence.
- **This property is not machine-checked at the moment.** A harness used to run the app's own tidy passes, tag parser and sentence scan over every recorded reply at five chunk sizes and require cut-as-it-arrives to equal cut-once-in-full; it was deleted with the rest of the diagnostic scaffolding. Any change to a tidy pass, a tag pattern or the sentence scan is therefore unguarded, and the failure it would produce — a segment the voice has already been given changing its mind — is silent.
- **The streaming early-out must never reach the end of the stream.** `absorb` returns `nil` without parsing when the arriving text cannot have changed the answer; that is worth 78.4% of chunks. `conclude` must not take it, because the end of the stream always settles the tail.
- **`spokenText` is only as fresh as the last full pass, so history must not read it.** `writeTheCurrentTurnIntoHistory` asks `spokenTextAsItStands()`, which re-runs the parse and the tidy over `rawTextAsReceived` on demand. Reading the cached value silently under-records an interrupted reply by exactly the chunks that were skipped.
- **A new question stops everything the last one started, and what was heard is what is remembered.** The teardown point is the one race-free moment to record the reply being replaced: everything above the history write is synchronous, and cancellation is cooperative, so the cancelled task's `catch` has not run yet and cannot run before the function returns. A stale chunk is the other half — cancelling a task stops it delivering but not instantly — which is what `turnIdentifierOfTheReplyBeingStreamed` is for. History records the **spoken** text with the tags stripped, never the raw reply: the raw text carries coordinates read off a screenshot that is already gone, and a history full of those is a set of worked examples teaching the model to point at last turn's screen.

### The turn as a loop of steps

- **`[LOOK]` is a group-free second alternative in the tag pattern, and that is not a style choice.** `:xN` is group 4, `:screenN` is group 5 and a drag's destination is groups 6 and 7 — all read by capture-group *position*, which is the same trap the drag's destination sits at the end to avoid. A marker that captured anything would move them and have `screenfuls(fromTagMatch:)` read a drop point's `y` as a distance. It is recognised by matching the text (`isTheLookMarker`) rather than a group, and the strip loop drops it without a stop for the same reason every other tag it cannot get a coordinate out of is dropped.
- **The speech segments and their indices are turn-scoped, and a step only ever appends its own tail to that list.** `speechSegmentsOfTheTurnBeingSpoken` holds the whole turn's narration in the order it is to be spoken, and `speechSegmentCountBeforeTheStepNowStreaming` is the step's own numbering base: `applyStreamedReplyIngest` rewrites the list as `prefix(base) + ingest.speechSegments`, hands the synthesiser `segmentIndex: base + settledSegment.segmentIndex`, and adds the same base to `finalizedSpeechSegmentCount`. This is the only reason a step boundary is not a seam — `currentSpeechSegmentIndex` is never reset there, so the voice finishes the last sentence of one step and walks straight into the first of the next. `speakPreparedSegment(segmentIndex:)` finds a prepared segment by index alone, so a step that numbered itself from zero would play the step before's first segment again, from a list that keeps what it has played.
- **The previous steps' segments have their stop range cleared as the ingest rewrites the list.** `stopIndexRange` indexes `resolvedPointingTourStops`, which is replaced per step, and `sentenceStartOffsetInSpokenText` is that step's own offset. An old range left on a segment of an earlier step would be compared against the running step's offsets the moment the new tour arms, and the cursor would fly to an element the narration has not reached. The segments themselves stay — they are what the voice is still reading — only their ranges go.
- **`isReplyStreamComplete` is cleared where the next step is asked for, not where its request goes out.** `askTheModelForTheNextStepOfTheTurn` sets it false beside `isProducingAReply = true`, before the compression and the capture. Left at the last step's `true` through that window — which is a compression and a screenshot wide — the previous step's final segment reaches `speakCurrentSpeechSegment` past the end of its list, reads the turn as finished, and ends the narration of the turn while a next step is already on its way; the panel shows 等待中 for the whole wait.
- **`isWaitingForTheFirstSoundOfTheReply` is armed only while the turn's voice is quiet.** A step asked for over the step before's audio sets it only `if !isSpeakingReply`, because that sound is the sound this flag is waiting for — armed over it, the flag would put the panel back into 处理中 while Kiki is audibly speaking.
- **The index may only move onto a segment that has already been cut, and `hasCurrentSpeechSegmentFinishedSpeaking` describes the segment the index is standing on.** `advanceSpeechIfPossible` moves onto `currentSpeechSegmentIndex + 1` only while that is below `finalizedSpeechSegmentCount` — or past the end of the whole list once `isReplyStreamComplete`. Stepped onto a segment still being written, `speakCurrentSpeechSegment` returns before it clears the flag, the next chunk reads the stale flag as "the segment after this one has been said" and steps over that one too, and the index goes on tracking the tip of the list: the rest of the step is never spoken, and every stop those segments named is never visited.
- **"This step's first segment" is `speechSegmentIndex == speechSegmentCountBeforeTheStepNowStreaming`, never `== 0`** — in a turn-scoped index space zero is the first segment of the whole turn and fires once. Two things hang off that test and both are per step: the narration's position is restated as zero, because it is counted in the text of the step the words belong to and the step before's whole narration outweighs an offset near the start of this step's, so a stop would read as reached and the cursor would fly ahead of the voice; and `schedulePointingTourFallbackIfNarrationIsSilent()` is armed, because the count it reads is cleared where a step's tour is armed and so starts again at every step.
- **`done` belongs to the turn, not to the stream, and moving it back would break the promise it makes.** `concludeStreamedReply` no longer sends it; `closeOutTheTurnBeingAnswered` does, because a turn is over when the cursor has finished acting rather than when the model stopped writing. The turn closes as soon as nothing further is coming, and nothing waits for the voice — a turn closes with its last sentence still being spoken, and the audio finishes on its own afterwards.
- **A turn's steps go into the conversation history one by one, so trimming it by entry count evicts the question a long search is answering.** Each entry carries `turnIdentifierOfTheTurnBeingAnswered`, and the trim drops from the front only while the front entry is not the turn in progress — so a turn's steps leave together however many there were. Cutting at `maximumExchangeCountCarriedInHistory` alone is the obvious thing and it fails silently: fifteen steps into a twenty-step search the original question is gone, along with every earlier exchange, and the model is left holding its own narration of what it was looking for.
- **There are two histories, and they are two faces of one task.** `conversationHistory` is the full record of the task, bounded only by `maximumExchangeCountCarriedInHistory` — a limit for a session that never ends rather than a working one. What a request *carries* is that history from `numberOfHistoryEntriesTheSummaryStandsInFor` on, with everything before it compressed into `summaryOfTheStepsCompressedOutOfTheContext`. The two are cleared together by the idle reset, because a summary left behind would be read as the record of a task the user has since walked away from. Anything that clears one and not the other is the bug this shape exists to prevent.
- **A history entry is a turn identifier and two strings, and no image ever enters it.** The screenshots go in the final `user` message of the step being asked about and nowhere else, so history turns are built as plain text and the picture a reply was written against is gone by the next step. What the model remembers of its own last action is the sentence reporting what it did, which is why that sentence has to name the element. It is also why the context grows slowly enough that the compression's trigger is measured in steps rather than in turns.
- **The summary is a count from the front of the same history, never a second copy of the conversation.** `numberOfHistoryEntriesTheSummaryStandsInFor` and the summary text are written together and mean nothing apart: the context is the summary followed by the history from that index on. A parallel array of "what the model has been sent" would be a second copy to drift from the first, and the drift would be silent — the model answering from a record that no longer matches what it was told.
- **The kept window starts at a turn's first step, and that is this codebase's form of the tool_call/tool_result pairing rule.** `indexWhereTheContextWouldStartCarryingTheHistoryWhole` starts `numberOfNewestStepsAlwaysCarriedWhole` back from the end and walks backwards while the entry it is looking at shares its `turnIdentifier` with the one before. A step that is not the first of its turn opens with the sentence reporting what the previous step's actions did, so a context beginning at one would open with a result whose call was cut away — an answer to something the model never saw itself ask. The walk-back is also why a turn longer than the whole window cannot be compressed at all: there is no boundary to cut on.
- **The summary is appended to the system prompt, never sent as a message of its own.** A summary standing among the history would either put two messages of the same role side by side or start the conversation on an assistant turn, and the API is entitled to refuse either. It also has to be counted in `estimatedTokenCountOfTheContextAsItStands` as part of the system prompt, or the compound it lives in grows past the room the trigger was measuring.
- **The trigger is checked before the screenshot is taken, and deliberately far below the limit.** The screenshots are the reason: `fractionOfTheContextThatStartsCompression` is 0.45 of a 1M context, which leaves the room a reply of up to `maximumOutputTokens` and a capture of every display need. Checking after the capture would spend exactly the round trip and the capture the compression was meant to save. The ratio is also what makes the output ceiling fit: 450K of input and `maximumOutputTokens`'s 384K are 83% of the window together. It fires far sooner than it sounds like it should — with the system prompt and a capture per display taken out, some 430K tokens are left for history, which is on the order of 700 steps of ordinary Chinese — so the compression is the structural bound on the context, and the idle reset is what ends most sessions before reaching it.
- **A compression that fails is not fatal, and one that lands after the question was replaced is dropped.** The request goes out over its own budget, which is what it would have done anyway, and the next step tries again with more behind it — so the failure costs nothing but a log line. The `Task.isCancelled` check after the await is the other half: the summary belongs to the conversation that asked for it, and a summary that came back after the question was replaced would be filed against a history that may be shorter, or about something else entirely.
- **The idle gap that starts a new conversation is measured from the last activity, not from the last thing the user said.** `dateOfTheLastActivityInTheConversation` is advanced by every step and by every turn's ending, because a search that runs for a quarter of an hour is the conversation still going. Measured from the user's own words alone, a long turn spends the whole idle budget on itself, and the follow-up asked the moment it ends reads as the user having been away — dropping the history the search had just built, the question it was answering included. The turn's ending is stamped where the turn is written into the history, so it must not move behind `hasWrittenTheCurrentTurnIntoHistory`'s guard.
- **The panel's task readout is refreshed where its answers change, never computed where they are read.** `taskProgress` is one value written by `refreshTaskProgress(includingThePrompt:)` from four call sites — a step starting, a compression landing, a round closing out, and the idle reset. The estimate walks every character of the conversation and the panel body re-evaluates on every chunk of the reply, so a read-through computation would put that walk on the main actor hundreds of times per reply. It is guarded like `settleVoiceState`, for the reason that one is.
- **A round enters the history once per step, so the panel's round count is the run changes in the array — and the running round is added only while its own first step has not been written yet.** From that write on the walk over the history has already counted it, and `numberOfStepsStartedInTheTurnBeingAnswered` is what says how many of the running round's steps are still to come. `tokenCountThatStartsCompression` is the one place the model's window and the compression fraction are combined, so the trigger the compression fires on and the one the panel counts down to are the same figure.
- **Every snapshot the terminal is sent is the whole turn, with the steps behind it prepended by hand.** The tool is promised absolute snapshots rather than deltas, so a snapshot of the current step alone would *shrink* the text the terminal has already read at every step boundary. The step's own half comes from `spokenTextAsItStands()` and not from the cached `spokenText`, for the reason the history write gives: the early-out means the cache is a full pass behind.
- **What the model is told its actions did is a sentence whose completion phrase is `completionPhraseForTheAction`'s.** Only the object differs from the terminal's sentence — a terminal may be a script looking for which occurrence was pressed, while the model is told about the element it named, because the element is the only thing in that sentence it can find on the next picture. A second phrase pool for the model would let a gesture added later be named for one audience and described only approximately for the other.
- **A report is dropped when the step it belongs to is no longer the one in progress.** `isStillTheStepIdentifiedBy` asks the turn identifier the streaming path already uses, because a click takes as long as it takes: a tour called off while one was in the air would otherwise file its report under whatever step happens to be running when it lands.
- **Whether an action reached the screen is `isASuccess` on the outcome, and it is the whole of what stops a `[LOOK]` from spinning.** A step whose every action was refused or failed has left the screen exactly as the screenshot its reply was written against, so looking again returns the same picture and earns the same reply. Each is a `switch` over every case rather than a comparison against the success case, so an outcome added later fails to build instead of reading as a failure.

### Pointing, clicking, dragging and scrolling

- **Whether an action happens is decided in exactly one place.** `actionThatWillActuallyBePerformed(at:)` in `CompanionManager` answers both halves — its answer is written into the flight as `PointingTarget.actionToPerformOnArrival`, which is what the overlay reads to choose between a pointing flight and the red carrying one, and it is what the path that posts the event performs. `requestedActionForArrival(at:)` is the one-clause form, so a **refused** action still reaches `ElementClicker` or `ElementScroller` and is reported as refused instead of disappearing. Two copies would be two answers to "does the red ritual happen" and "does an event go out", the pair that must never disagree.
- **There is one gap between the presses of one multi-press gesture, `ElementClicker.secondsBetweenThePressesOfOneGesture`, and everything that asks for two or three presses goes through `kind: .doubleClick` or `kind: .tripleClick` to reach it** — the model's `[DOUBLECLICK:…]` and `[TRIPLECLICK:…]` tags, and `kiki doubleclick` and `kiki tripleclick` alike. It is bounded from above by `NSEvent.doubleClickInterval`, which the user can turn down to about 0.15 s, and from below by non-zero, because events posted back to back carry timestamps microseconds apart. A second interval is silent in both directions: too long and the app sees unrelated clicks — a file merely gets selected instead of opening, and a triple click selects nothing — and too short and the later press is not a further click at all, so the click count never reaches three.
- **A click gesture is which button goes down and how many times, and `ElementClickKind` is the only place those two are decided.** `buttonThatIsPressed` is the sole gesture-to-button mapping and `numberOfPresses` the sole gesture-to-count one; a caller passes `kind: .rightClick` and reaches neither. Adding the right button as a third kind rather than as a flag beside a press count is what keeps the button, the presses and the phrase pool from each needing an answer of their own. `numberOfPresses` is a `switch` over every kind rather than a `self == .doubleClick ? 2 : 1`: the ternary answers 1 for any kind added later, so a new press count would compile, run, and quietly press once.
- **The event type and the button must change together, and this is the only silent failure in the click itself.** `.rightMouseDown` carrying `.left`, or `.leftMouseDown` carrying `.right`, is delivered to the *other button's* handler — so the event goes out, the log fills, and the wrong button was pressed. `mouseEvents(forOneClickWithClickState:using:atAccessibilityScreenPoint:)` derives both from its `button` argument for that reason; a probe watching a click has to log `mouseDown` and `rightMouseDown` separately or it cannot tell the two apart either.
- **A flight is one value, not five writes.** `PointingTarget` carries the point, the display frame, the bubble invitation, the bubble text and the action to perform on arrival together, because they are one answer: written separately, a flight that failed to overwrite one of them would point at the right place for the wrong reason. The overlay watches `screenLocation` alone and reads the rest on arrival, which is what lets the action be withdrawn — not merely unset — when the tour ends under the cursor.
- **A click's three refusals are decidable from the caller's own words plus one permission flag**, which is what `ElementClicker.refusalOfClick(matchingElementLabel:origin:)` exposes: no label, a label naming something irreversible, or Accessibility not being granted. Only the first is origin-dependent — `ElementClickOrigin.theModelsTag` refuses a click with no label because the label is the only way to find the element, while `.theUsersOwnCommand` (`kiki click -x -y`, or the same point asked for as either of the other two presses) *is* a point and has no label to give. The other two apply to both, so a terminal click naming 删除 is refused exactly as the model's would be. Both the click sound and the red carrying flight ask it *before* acting, because both say "I am about to press this" — and a refused click that made the sound, or did the ritual, would say the opposite of what happened. A **scroll** has one refusal instead, `ElementScroller.refusalOfScroll()`, and it is Accessibility alone: scrolling back undoes a scroll, so the destructive-word rule that guards a click has nothing to protect here, and a scroll naming 删除 goes through. A **drag** has two, `ElementDragger.refusalOfDrag(toAppKitScreenLocation:)`: no destination was named, and Accessibility — the same reasoning as a scroll for the missing destructive-word rule, plus a destination that is a bare point and so has no label for that rule to read.
- **The click carries its own point.** Each `CGEvent` holds the point it is aimed at, so the click lands where the event says rather than where the mouse happens to be standing. Moving the pointer and posting the click are independent; the carry exists for the user's benefit — an app that hit-tests against the physical pointer finds it where the event is — not for the click's.
- **A drag is one event per step, never one jump to the destination.** `ElementDragger.dragElement` posts a `leftMouseDown` at the start, `stepsInOneDrag` interpolated `leftMouseDragged` events, and a `leftMouseUp` at the destination, one every `secondsBetweenTheStepsOfADrag`. A single dragged event at the destination is a movement no target ever saw pass over it, and a target that follows along — a list reordering under the pointer, a folder highlighting as something is carried onto it — has nothing to follow. The whole gesture is therefore about half a second, which is also what `screenLocationOfTheDragInFlight` reports step by step so the cursor is drawn travelling with it.
- **The Accessibility hit test is a witness, not a gate.** It is still run at the point and its findings are written to the record, because that is what makes a click that landed somewhere unexpected answerable afterwards. Nothing a tree says is grounds to withhold a click: a mechanism that cannot press a verified, correctly located element is a defect, not a safety property.
- **`CGWarpMouseCursorPosition` detaches the physical mouse from the pointer for about a quarter of a second and re-attaches on its own.** That is why the hard hold is `CGAssociateMouseAndMouseCursorPosition(false)` and not a warp, and why every teardown path has to release for real. A detachment outlives the process that made it, so `CompanionAppDelegate` calls `PointerCarrier.reattachTheMouseUnconditionally()` at launch and at terminate — **unconditionally**, because the in-flight flag belongs to the dead process and reads `false` at exactly the moment a guarded call would be needed.
- **A carry is held across a whole run, including each dwell; the hard suppression is only on the carrying legs.** During a dwell the user can push the pointer away, and that means they are taking over. The next carrying leg recovers it with a warp rather than flying out to fetch it, because a flight out is the "leaving the mouse" gesture that was explicitly not wanted mid-run.
- **The model names the element; the app says where it is.** `ScreenshotTextRecognizer` finds the tag's label on screen and the pixels come from the screen, because the model reads a recognizable shape off an image essentially exactly but *estimates* a position it has to measure. The label instruction in the prompt is load-bearing: a label that is not verbatim simply does not match, and the pipeline silently reverts to the model's own estimate.
- **A gesture's tag name has to be added in three places, and missing the second is the silent one.** The pattern in `parsePointingCoordinates`, the prefix branch in `pointingBubbleInvitation(fromTagMatch:in:)`, and the prompt paragraph that tells the model to write it. Without the second, the tag still parses and the click still goes out — the cursor flies and presses correctly — but the bubble says 「看这里！」 over a gesture the user did not ask for. Without the third, nothing writes the tag at all. The alternatives in the pattern are anchored just after `\[` so that `CLICK` cannot swallow `RIGHTCLICK:`. A gesture reachable from the terminal needs **four**: `actionAskedForByTheTerminal`'s `default: return nil` refuses a gesture it does not name, so a missing case there answers `kiki` with 「这个手势 Kiki 不认识」 while the model's tag of the same name works.
- **A readiness flag lives in four places and only three of them are caught by the compiler.** `KikiCommandReadiness` is a `let`, so both of its construction sites in `CompanionManager` fail to build; the CLI's read site fails to build as well. `KikiCommandEvent` is not: its fields are `var` optionals, so a memberwise initialiser defaults the new one to nil, and the copy inside `KikiCommandEvent.ready(_:)` is written by hand. Miss that copy and the field is never sent — every terminal is told the running app is too old, which is exactly the refusal the flag exists to make true.
- **A scroll's distance carries an `x` prefix, and without it the tag is silently a different tag.** `[SCROLLDOWN:640,400:消息列表:x3]` is three screenfuls; a bare `:3` is not, because everything after the second colon is the label's lazy capture group and the label swallows the digits — `[RIGHTCLICK:120,240:今天 02:04]` is the live example of a label containing a colon and a number. The pattern therefore reads label, then `(?::x(\d+(?:\.\d+)?))?`, then `(?::screen(\d+))?`, and the prompt asks for that order. The distance may be fractional and **its inner group must be non-capturing**: `(\.\d+)?` would add a capture group in the middle of the tag, shifting `:screenN` and a drag's destination one position along, and the drop point's `y` would be read as a screen number. A swallowed distance is silent twice over: the label no longer matches anything on screen, so the coordinate falls back to the model's own estimate, and the scroll reads as one screenful.
- **The sign of a scroll lives in exactly one place, `ElementScroller.wheelDeltas(for:byPoints:)`, and it was measured rather than reasoned about.** A wheel event carries deltas, not a direction, and which sign moves which way is the one thing about this that cannot be read off the source; a synthesized wheel is in the same space a trackpad reports. A screenful is `fractionOfTheDisplayOneScreenfulCovers` of the display's height for up and down and its width for left and right, so the number differs by direction, and one event goes out per screenful rather than one large delta — a fractional distance sends one event per whole screenful plus a smaller last one for the remainder, which is what makes half a screen travel half as far rather than a whole one rounded down.
- **A distance becomes words in exactly one place, `ElementScroller.screenfulsAsText`.** The terminal's 「已往下滚 0.5 屏」 and the bubble's 「帮你往下滚 0.5 屏」 are both cut from it, so the gesture is described the same way to both audiences. Whole numbers go through `Int` rather than printing as `1.0`, which is what the commonest case — a bare tag, or a `-b` left alone — would otherwise become. A `0.5` is the smallest distance a request may name (`smallestScreenfulsInOneRequest`, against a ceiling of `mostScreenfulsInOneRequest`), both as the tag parser's clamp and as the tool's own limit; the two must move together or a request the tool sends comes back as a scroll of some other distance.
- **A wheel event is aimed by the point it carries, and posting one still moves the pointer.** The point on the event decides which window receives the scroll — the window under *that* point, not the one under the pointer — which is the same rule a click follows. But the two part company on what else happens: every tap that delivers a synthesized scroll also drags the pointer to the event's point, and the one tap that leaves the pointer alone delivers nothing at all. That is why a scroll cannot be aimed somewhere with the user's pointer staying put, and why `ElementActionOnArrival.carriesTheUsersPointer` is `true` for a scroll as well — the carry is what makes the jump read as a gesture rather than a teleport. A drag carries the pointer for that same reason and one more: the pointer has to *arrive* somewhere for the drop to have been made at all.
- **A drag outlives the arrival, and everything that closes a flight on arrival would cut it short.** `buddyDidArriveAtPointingTarget()` hands the tour on and drops the flight the moment the cursor lands, which for a drag is the moment the button goes *down*: closing there puts the cursor on the next stop with the mouse still held. So that function asks whether this arrival is the start of a drag (`isStartingADrag`, read off the stop's or the terminal's action) and, if it is, cancels the arrival watchdog and leaves the closing to the drag itself, which does it when the last step has been posted. That closing is guarded by `isFlyingToPointingTourStop`, so a watchdog that fired first cannot close the same flight twice and skip a stop. The watchdog goes with the closing for the same reason it exists: while a drag is running nothing is in flight for it to be watching.
- **A drag's destination is the last thing in the tag pattern, and the numbering is why.** `screenfuls(fromTagMatch:)` and `screenNumber(fromTagMatch:)` read their numbers by capture-group position, so a destination added anywhere but the end would have them read the drop point's `y` as a distance or as a screen number. `dragDestinationScreenshotCoordinate(fromTagMatch:in:)` also checks the tag is the drag's own, because those groups belong to the one pattern every tag shares and would otherwise be read off a tag that has no destination.
- **A drag's destination is a bare point, so it is neither sharpened nor allowed to leave the starting screen.** There is no text at the drop point for `ScreenshotTextRecognizer` to find, which is why the prompt has to ask for it measured rather than estimated — the element's own coordinate survives being an estimate because the label overrides it, and this one does not. It is converted from the *starting* stop's screenshot, and `screenLocation(forScreenshotCoordinate:on:)` clamps to that capture, so a model-written destination cannot land on another display; the terminal's can, and that is what the one cross-screen check in `carryOutTheActionTheTerminalAskedFor` is for.
- **An unrecognised `gesture` is a refusal, never a click.** The field once meant "which click", so an unknown value fell back to a single left press — harmless while every value was a click, and not now: a `scrollDown` reaching an app built before scrolling existed would press the left button on whatever the terminal aimed at, which on a link navigates and on a dialog loses work. A *missing* `gesture` still means a plain click, because that is what a tool predating the field sent. `KikiCommandReadiness.understandsScrolling`, `understandsTripleClick`, `understandsDragging` and `understandsFractionalScreenfuls` are the same trap read the other way round, and they exist because the commonest way to meet it is rebuilding without restarting: a new tool against a running old app has to be refused before it sends, not after. The drag is the worst of the three gestures to get wrong, because an old app decodes the destination fields and ignores them: the drag then arrives as a press at the starting point, which on a file selects it and on a folder opens it. The fractional screenful is worse still and is why it needs a gate of its own — `screenfuls` was `Int?` before it, so a `0.5` does not degrade, it fails to decode the whole request, and a dropped connection is exactly what Kiki going away looks like to the tool. The tool asks one question of them — `gestureTheRunningKikiDoesNotKnow(_:readiness:)` answers the *name* of the gesture the running app does not know, and the sentence is written at the call site, because there is only one sentence.
- **"Standing alone as a word" is asked only of characters that could be in the same word.** A neighbouring character demotes a match only when it is a letter or a digit *and* written in the same writing system as the character it touches. Chinese writes no spaces, so a label inside a longer run of Chinese still ranks below the same label on its own — but an OCR-invented Latin `v` glued to the end of a Chinese label no longer counts as continuing it. Without that qualifier the cursor flew 136 pixels to a different element while the right one sat 35 pixels from the coordinate the model gave.
- **A box an earlier stop has already been flown to is spent.** Stops are scored independently, so the tour passes in the rectangles earlier stops of the same tour resolved to and a candidate overlapping one is passed over as though it had not matched. Otherwise five stops naming five identical labels collapse onto shared rows.
- **Logics that only matter for a configuration you do not currently have must still be kept.** Multiple displays, mirrored screens, extra transcription providers: "I don't plug one in right now" is not "I never will". Multi-monitor handling in particular is not to be deleted on the grounds that only one screen is attached today.

### Recording and replaying the user's own actions

- **A replayed action is an `ActionBeingWaitedOn` whose `whoHearsTheAnswer` is `.theReplayOfTheUsersRecordedActions`, and it must stay one.** A tag, a terminal and a replay all reach `ElementClicker` / `ElementScroller` / `ElementDragger` through the same flight and the same arrival; a second path for the replay would be a second answer to "does the red ritual happen" and "does an event go out", the pair that must never disagree. That is also why the flight value is named for the action rather than for the terminal that asked for it.

- **The replay contains no press/scroll/drag switch of its own, and adding one is the failure this design exists to prevent.** The action travels as one value and the button, the number of presses, the direction, the distance, the bubble and the pointer carry are all read off it, so a recorded action needs no translation layer — and a translation layer would be the thing that drifts.

- **A recorded scroll replays through the same `ElementScroller` as everything else, which is why a distance is a unit inside `ElementScrollDistance` rather than a second `ElementActionOnArrival` case.** Most switches over the action carry the distance rather than reading it, so a `.scrollByPoints` case would add a duplicate arm to every one of them and tell the two places that do read it nothing new. `.points` is what the recorder produces and `.screenfuls` what the model's `:x3` and `kiki scroll -b` produce — a screenful count that may be fractional, whose conversion to points happens inside that same case so neither of those two callers knows the display's height; nothing new travels over the command socket, so no `KikiCommandReadiness` flag goes with this.

- **`secondsBetweenReplayedActions` must stay below `pointingTourStopMaximumDwellSeconds`.** Each arrival schedules the return-home watchdog, and a gap longer than the watchdog lets the cursor start flying home between two steps and be pulled away mid-flight.

- **A tap that stops a replay also has to call off the step already in flight.** A step spends its first half resolving the point and its second half flying, so cancelling the scheduled next step is not enough: the loop would still press one more thing after being told to stop, which says the opposite of what the tap said. The call-off belongs to the tap and not to `stopRecordingOrReplayingAndForgetIt()` — that function's other callers hand it their own sentence for the interrupted action, and a second one written inside would never be heard.

- **Ending a replay must hand the pointer back at once, not wherever the flight in the air happens to land.** A replay is a run of pointer-carrying flights, so the user's pointer is in Kiki's hand at almost any moment a tap could end one, and a flight releases only at its destination. `stopRecordingOrReplayingAndForgetIt()` clears the cursor's target and asks for the cursor home — the same restoration `abandonSpeakingReply()` does for a reply — which releases the carry on the same tick; without it the tap drags the pointer to something nothing is going to press and holds it through the tour's return-home watchdog.

- **A continuous scroll event's movement is in `scrollWheelEventPointDeltaAxis1/2`, never in `scrollWheelEventDeltaAxis1/2`.** For a trackpad the plain delta is that movement divided by about ten and rounded to a whole number — one event of a real flick held `delta1 = -2` beside `pointDelta1 = -26` — so a recording read from it replays every flick at a tenth of the distance covered, silently, because the axis and the sign are both right. `fixedPtDeltaAxis1` is the same approximation with its fraction kept, and the one case that needs the plain delta is the line-based wheel, multiplied by `pointsPerLineOfALineBasedWheel`. Both fields are read as doubles: a trackpad reports fractions of a point, and reading them as integers turns a slow scroll into no scroll at all.

### Resting in the status item icon

- **The icon's merged image must not be a template image.** A template image is the system's to tint, and it would recolour the purple back to black or white with nothing to show for it — the visit's only visible half gone silently. `isTemplate = false` goes on with the purple fill and comes back off with the plain black one.
- **Both waits are gated on an arrival, and their two latches are cleared together in `beginStatusItemIconMerge`.** The pointer must have left the icon since the last visit before the resting wait counts, and must have left the waking range before the waking wait does. Without them a pointer parked on the icon satisfies a gesture whose timer has just run out, and the cursor flies in and out every three seconds on a mouse that never moved — which reads as working.
- **Every way into the app reads one property, `isNotTakingInputBecauseOfTheStatusItemIcon`** — the shortcut's `.pressed`, `commandReadiness()`, `runCommandFromTerminal`, `replayOnboarding()`, `startRecordingWhatTheUserIsDoing`, and the overlay's `startNavigatingToElement`. It is `statusItemIconPhase != .notInTheIcon`, so resting and waking are covered by construction rather than by two lists that can drift. `.released` is deliberately not gated: the cleanup for a press that never started still has to run, or the waveform stays on screen.
- **The waking range is derived from the icon's frame, read fresh every tick, so an off-screen icon puts it out of reach and Kiki rests until the icon is back.** Hidden Bar parks the icon at x≈-4310 and a full-screen app hides the menu bar; both leave the visit standing. That is intended — a cleanup on "the frame is on no screen" would fire on every one of those, and Kiki does not react to what the window server does with the menu bar.

### Concurrency and the main actor

- **`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` is set on the target.** An unannotated declaration is implicitly main-actor isolated, so an `await` on it from main-actor code does not leave the main actor — `ElementClicker`'s un-awaited `Task` buys concurrency, not a thread hop, which is why its Accessibility hit test has a 0.5-second messaging timeout. `nonisolated` is what this codebase reaches for when something genuinely must run off the main actor.
- **Actor isolation is transitive, so work hung off a `@MainActor` type runs on the main actor by association — and the overlay is animating there.** This has bitten twice: a diagnostic recorder that wrote a file per spoken word, and the screenshot JPEG encode, tens of milliseconds per display, both landing in the window where the overlay animates the waveform away and the spinner in. Neither was slow in isolation; both were on the thread doing the drawing. Put work like that on a `DispatchQueue` of its own and cross only the bytes. A serial queue is the right choice where the output is read as a timeline and reordering would cost more than the writes do.
- **`VNImageRequestHandler.perform` is synchronous and blocks for the better part of a second.** Called inside an `async` function it occupies one of Swift's cooperative-pool threads, which is the same pool that delivers the streaming response — so it held the whole reply, and `serverFirstByte` was never a measurement of DeepSeek at all. `ScreenshotTextRecognizer` runs it on a concurrent `DispatchQueue` reached through `withCheckedContinuation`, and recognition starts the instant the screenshots are captured rather than when the tags need converting.
- **`AXUIElementSetMessagingTimeout` on the *system-wide* object sets the timeout globally for the process**, not just for calls on that object — which is the only reason the single call in `ElementClicker` bounds the Accessibility hit test too. The hit test is answered by whichever app owns the window under the point, so one unresponsive app could otherwise stall the main actor for seconds.

### The command line tool

- **Both ends set `SO_NOSIGPIPE`.** A terminal that Ctrl-C'd leaves a closed socket, and the next write to it raises `SIGPIPE`, whose default action is to kill the process — the whole app, for a hung-up reader. It is not a permissions flag or a nicety; without it `kiki command` can take Kiki down with it.
- **An accepted socket inherits the listening socket's `O_NONBLOCK`, so `SO_SNDTIMEO` on it bounds nothing.** A write gives up the moment the send buffer — a few kilobytes — is full, and `EAGAIN` is then the same answer for a terminal that is merely between reads and one that has gone. `writeLineToClient` therefore waits for room with `poll` and writes the rest of the line, releasing a terminal only after it has taken nothing for the whole timeout. Reading a short write as "this client is dead" instead hangs up on a live terminal mid-reply, and the only thing that terminal can say about it is 「和 Kiki 的连接断了」 — which is exactly what Kiki going away looks like. A snapshot of a long reply is hundreds of kilobytes in total, so the buffer really does fill.
- **A socket file outlives the process that bound it, and both ends have to plan for that.** The app `unlink`s the path before binding, or a crash would leave the next launch unable to bind. The tool has no case of its own for a stale file, because connecting to one answers `ECONNREFUSED`, which is the same answer as "not running" — and the response to that is to launch the app, which is right either way.
- **Displacement is a property of the request, not of the connection, and it is announced before the old connection is closed.** Only a `command` claims the reply-watching role and takes it from whoever held it, because the two ways a person talks to Kiki — a typed command and Control+Option — are the ones that interrupt what is running and everything else yields to them. A gesture — `kiki click`, `kiki doubleclick`, `kiki tripleclick`, `kiki rightclick`, the four scrolls and the drag, all the same in this — takes no role and displaces nothing, not even another gesture's, so one arriving while a reply streams leaves the terminal watching it alone. A displaced terminal otherwise sees only that its connection closed — which is exactly what it would see if Kiki had died, and the two happen at the same instant, so asking afterwards whether the app is still running does not separate them either. The app sends `superseded` first, and that message is the only thing that makes a hang-up readable: **no `superseded` means Kiki went away.**
- **An answer to "the terminal" is really an answer to whichever terminal holds that role, so every answer names the terminal it belongs to.** The reply stream goes to the one watching the reply, a click's answer to the one that asked, even while somebody else's reply streams undisturbed beside it. Nothing is ever addressed to "whichever connection is attached" — that phrasing is what made a click's answer land on a terminal whose question was different, and what made a second click able to overwrite the first one's pending answer. A terminal that has closed is simply not in the table, so it is not answered anywhere else either: the click it asked for is still made, and nobody hears about it.
- **`ready` judges exactly two things — the API key and Screen Recording — and never Accessibility.** No Accessibility means clicks are refused and reported as refused; it does not mean Kiki cannot see, answer or point. Adding it here would make a missing grant block a path that works fine without it.
- **The streaming send point is gated on `hasATerminalWatchingTheReply`, and that gate is the whole reason the change is free.** `spokenTextAsItStands()` re-runs the entire tag parse, which is exactly what the streaming early-out exists to skip; asking per chunk with no terminal watching would spend the 78.4% saving for nobody. With no terminal ever attached, not one byte of app behaviour changes. It is named for the role rather than for the connection because a click's connection is a connection too, and nobody is watching anything through it.
- **`hasATerminalWatchingTheReply` is read through an `NSLock`, not `queue.sync`.** The serial queue can be inside a `write` waiting for room for up to `sendTimeoutSeconds`, and the reader is the main actor — the same actor the overlay animates on — so waiting on that queue is not an option.
- **The transcript is `spokenTextAsItStands()`, the same string that is spoken and written to history.** Tags are stripped, so the terminal never sees `[POINT:…]` coordinates read off a screenshot that is already gone.
- **The tool launches the app with `/usr/bin/open`, never by running the binary**, and without `-n` — the same TCC attribution rule as everywhere else, plus a second menu bar icon if a second copy started.
- **A command from the terminal is silent unless it passed `--speak`, and that one flag is the whole difference.** Nothing is synthesised and nothing is played; the reply still streams to the terminal, still goes to history, and still flies the cursor to every tagged element. `isReadingTheReplyAloud` is set per turn by `sendTranscriptToClaudeWithScreenshot`, so it never outlives the turn that asked for it, and a dictation turn takes the default of `true`.
- **A silent turn must never reach `speakPreparedSegment`.** The pointing is paced by the narration — every tour flight is triggered by a word report or by a segment being spoken through — so `speakCurrentSpeechSegment` marks each segment spoken through itself when there is no voice, and the cursor becomes the only thing pacing the tour. Handing the segment over anyway would hang the reply instead of failing it: `speakPreparedSegment` waits with no deadline at all for a closing buffer that a silent turn never produces. The dwell is shorter in that mode (`minimumSilentPointingTourStopDwellSeconds`), because there is no sentence the bubble has to keep pace with.
- **`kiki click` answers the same question as `kiki command` in the opposite way, and the other eight gesture subcommands are `kiki click` with the gesture changed.** `command` exists partly to displace whatever is running — a new question stops the last one. A click displaces nothing: when Kiki is not 等待中 it is refused and the mouse does not move, and its connection claims no role, so a terminal watching a reply keeps watching it. `runActionFromTerminal` must not be routed through `runCommandFromTerminal`, because that function's first act is the teardown. A click builds no task, touches no pointing tour and writes no history; its only intersection with the reply pipeline is that both post an event. Being called off — by a command's teardown, or by the push-to-talk key — is reported to the terminal that asked and exits **2**, the code `kiki click` already uses for "Kiki said no", because a click that was interrupted was not made.
- **The action asked for travels as one value — `TerminalActionInFlight.action` for a terminal, the tag's name for the model — and the bubble, the button, the number of presses, the direction, the distance and the sentence the terminal is answered with are all derived from it.** `PointingBubbleInvitation.describing(_:)` is the only place a gesture becomes its phrase pool — 「点这里！」, 「双击这里！」, 「三击这里！」, 「右键这里！」, 「帮你往下滚！」, 「帮你拖过去！」 — and `completionPhraseForTheAction(_:)` the only place it becomes 「已点击」, 「已双击」, 「已三击」, 「已右键点击」, 「已拖动」 or 「已往下滚 3 屏：」 (with `phraseForScrolling` the only place the direction and distance become 「往下滚 3 屏」, said the same way in the bubble). Written separately they drift into a bubble saying 「点这里！」 over two presses, which is the one thing the separate pools exist to prevent: the gestures look identical on screen until they happen. Deriving it also means `kiki rightclick` reaches `ElementClicker` by passing `kind: .rightClick`, `kiki scrolldown -b 3` reaches `ElementScroller` with that distance, and `kiki drag --to-x --to-y` reaches `ElementDragger` with that destination, rather than by a second path to any of them. The drag's destination is the one thing that does *not* live in this value: it travels beside the action, on the stop or on the terminal's request, because it is a point and `ElementActionOnArrival` is an AppKit-free type the overlay reads.
- **A second action arriving while one is still in flight is refused by a guard of its own, never by `whyAnActionFromTheTerminalCannotBeMadeRightNow`.** That property is asked a second time, in `carryOutTheActionTheTerminalAskedFor`, after the screenshot has been taken — and by then the action being waited on is that very action, so a rule living there would have every request refuse itself. It also comes last among the refusals, after the ones about the request itself, so a terminal asking for something Kiki will never do hears that rather than a wait it could not shorten by trying again.
- **The "Kiki 正在看屏幕…" line is printed on the app's `accepted`, never ahead of it.** Every refusal decidable without looking at a screen — not 等待中, another action still in flight, 「允许 Kiki 用鼠标操作」off, a destructive word, no Accessibility — is answered in milliseconds and captures nothing, so a line printed as the request was sent would promise a screen look in exactly the cases where none happens. `runActionFromTerminal` sends `accepted` once those refusals are behind it and before the capture begins, which is what makes the promise true when it is made. The refusal that *does* need the screen (no such text, no such occurrence) comes after it, and is honestly preceded by it. The sentence travels in `accepted(message:)` and is written in `CompanionManager` with the rest of Kiki's sentences; a terminal that asked by coordinate is sent `accepted(message: nil)`, because a press by coordinate is answered in milliseconds and has no wait to be told about.
- **A gesture's stdout is what Kiki says about the action; this tool's own sentences go to stderr.** The nine gestures produce no reply, so their stdout is free — 「已点击「确定」（第 1 个）。」 is the whole product of the command, and a script asking where the press landed has nowhere else to read it. The split is by *origin* rather than by kind: anything out of `event.message` is the app's and goes to stdout, and a flag misspelled, no app found, a dropped connection or a wait that ran out is the tool's and goes to stderr. `kiki command` is the exception, and only because its stdout is already spoken for: the reply streams there, so even the app's `accepted` sentence goes to stderr. The cost of not keeping a fallback string in the tool is that a new tool against an app built before `accepted(message:)` prints no 「正在看屏幕」 line at all — the older app sends an `accepted` carrying no message and there is nothing to print — which is the price of not holding a second copy of a sentence that is Kiki's.
- **A subcommand returns its exit code; only the entry point ends the process.** `runCommandSubcommand` and `runClickSubcommand` both return `ExitCode`, so what each can exit with is in its signature and the one `switch` at the bottom of `main.swift` is the only place a code becomes a process status. `fail`, `failWithUsage` and `usageAndExit` stay `-> Never`, because every call site is a diagnosis made before the request goes out: there is no answer in flight to collect and nothing to unwind.
- **Whether an action may start is `voiceState == .idle` plus `statusItemIconPhase == .notInTheIcon`, and deliberately not "the cursor is home".** `finishSpeakingReply()` writes `.idle` *before* the cursor is called back, so for a few seconds Kiki reads as 等待中 with the cursor still in flight — and that is deliberately allowed, because an event carries its own point and nothing is waiting on the pointer. The same fact is what makes consecutive `kiki click`s not return the pointer home in between: each command returns when its event is posted, and the return-home timer only runs once nothing else is asking.
- **Only the app may post the event.** `CGEvent` is attributed by TCC to the process that posts it, so a click, scroll or drag synthesized inside `kiki` would be judged against the terminal. The tool has no code path that can click, scroll or drag; it can only ask.
- **The tool does not consult `canRunCommands` for a click.** That flag answers whether a *request* can run — API key and Screen Recording. A click needs neither, and gating on it would block a path that works without them. What the app can do right now is answered by the app, in the reply to the click itself.
- **The screen numbering is the screenshot order, and there is no second one.** `CompanionScreenCaptureUtility.captureAllScreensAsJPEG()` puts the pointer's screen first and the model's `:screenN` tags are written against that order; `-n` and `-s` count the same list. A `-n` counting some other order would point at a different screen's word while reporting success.

## Build & Run

The project directory, the `.xcodeproj` and the scheme are all `kiki-desktop-agent`; the app itself is `Kiki.app`, because `PRODUCT_NAME = Kiki`. The two names are deliberately different — the directory says what the project is, the product says what the user sees — and `PRODUCT_NAME` is what the test targets' `@testable import Kiki` has to match.

```bash
# Open in Xcode
open kiki-desktop-agent.xcodeproj

# Or build from the terminal (produces Kiki.app and kiki in DerivedData)
xcodebuild -project kiki-desktop-agent.xcodeproj -scheme kiki-desktop-agent -configuration Debug \
  CODE_SIGN_IDENTITY="Smarty Kiki Signing" \
  CODE_SIGN_STYLE=Manual \
  DEVELOPMENT_TEAM="" \
  build

# Known non-blocking warnings: Swift 6 concurrency warnings,
# deprecated onChange warning in OverlayWindow.swift. Do NOT attempt to fix these.
```

The `kiki-desktop-agent` scheme is a **shared** scheme and builds both targets into the same `Build/Products/<configuration>/`, which is what lets the tool find `Kiki.app` as a sibling of itself. It is checked in at `xcshareddata/xcschemes/` deliberately: the automatic schemes xcodebuild generates are one per target, so without it `-scheme kiki-desktop-agent` would build the app and silently leave the tool stale. Building only the tool with `-scheme kiki` also works, and needs no app rebuild.

**Running `xcodebuild` from the terminal is safe.** It used to invalidate TCC permissions on every rebuild, which was a consequence of ad-hoc signing: an ad-hoc signature's Designated Requirement is a bare `cdhash`, so every rebuild produced a different identity as far as TCC was concerned. The self-signed certificate below replaced that with a certificate-anchored requirement that is stable across rebuilds, so grants survive. **Launch with `open …/Kiki.app` when the permission state matters** — see "Rules That Bite If Broken" for why running the binary from a shell breaks it.

### Code Signing (self-signed certificate)

The app is signed with a local self-signed certificate named `Smarty Kiki Signing` rather than a real Apple Developer certificate. Nothing requires a Developer certificate — the app is never distributed and needs no provisioning profile — and the self-signed one is what makes TCC grants stick:

```
designated => identifier "com.smarty.kiki" and certificate root = H"ee5a2ca6f89d8ca593a7ccf0582da31449acaa83"
```

The `certificate root` clause is the point: it names the certificate, not any particular build, so a rebuilt binary still satisfies the requirement TCC recorded. An earlier certificate (`Clicky Local Signing`) is no longer in the login keychain, so builds naming it fail outright. Any future certificate swap costs one round of re-granting, then continuity resumes.

One build setting exists only because a self-signed certificate has no Team ID, and it is load-bearing — the app fails to launch without it:

- **`ENABLE_DEBUG_DYLIB = NO`** on Debug. Xcode's debug-dylib feature splits a Debug build into a stub executable plus `Kiki.debug.dylib`, and hardened runtime's library validation rejects that pairing when neither side carries a Team ID ("Library not loaded: @rpath/Kiki.debug.dylib"). Release builds are already a single binary and need nothing.

There used to be a second one, `com.apple.security.cs.disable-library-validation`, which existed solely so the embedded `Sparkle.framework` could load. Sparkle was removed, and with no third-party framework left to embed there is nothing for library validation to reject — so the app now runs under the **full** hardened runtime. Do not reintroduce that entitlement without something concrete that needs it.

**`ENABLE_CODE_COVERAGE = NO`** is set on the project's Debug and Release configurations, and `kiki` depends on it. Coverage turns on LLVM's profile instrumentation, whose runtime writes a `default.profraw` into the process's working directory at exit — so every `kiki click` and `kiki command` would drop a file in whatever directory the caller was standing in. The app is unaffected either way: `/usr/bin/open` gives it `/` as its working directory, where that write fails silently.

The app binary still carries `__llvm_prf_*` sections anyway, and they come from the PostHog package rather than from this project: SPM package targets do not inherit the project's build settings, so they keep the toolchain default of coverage on, and their merged objects pull the profile runtime into the link. Nothing here can change that, and nothing needs to.

**Bundle identifier is `com.smarty.kiki`.** The DeepSeek API key lives in a Keychain item keyed on it.

## Code Style & Conventions

### Variable and Method Naming

IMPORTANT: Follow these naming rules strictly. Clarity is the top priority.

- Be as clear and specific with variable and method names as possible
- **Optimize for clarity over concision.** A developer with zero context on the codebase should immediately understand what a variable or method does just from reading its name
- Use longer names when it improves clarity. Do NOT use single-character variable names
- Example: use `originalQuestionLastAnsweredDate` instead of `originalAnswered`
- When passing props or arguments to functions, keep the same names as the original variable. Do not shorten or abbreviate parameter names. If you have `currentCardData`, pass it as `currentCardData`, not `card` or `cardData`

### Code Clarity

- **Clear is better than clever.** Do not write functionality in fewer lines if it makes the code harder to understand
- Write more lines of code if additional lines improve readability and comprehension
- Make things so clear that someone with zero context would completely understand the variable names, method names, what things do, and why they exist
- When a variable or method name alone cannot fully explain something, add a comment explaining what is happening and why

### Comments

- **Comments explain why, not what.** If a comment is needed to say what a line does, rename the thing instead. Code that reads plainly needs no comment above it.
- **English in code, Simplified Chinese for anything the user reads or hears.**
- **Keep only what a reader cannot get from the code:**
  - System behaviour that is not visible in the source — a framework call that does something else as a side effect, a timer that stops firing in a particular run loop mode.
  - Why an obvious alternative is not usable, in one sentence.
  - Why a constant has the value it has, when it would otherwise look arbitrary.
  - "There must not be a second copy of this" warnings.
- **Delete the discovery narrative.** How something was found, what it measured, how many times it reproduced, what the old design did and why it was replaced — none of that belongs in the source. The *conclusion* stays if it justifies a constant or a shape; the process goes — and it goes for good, not into some other file.
- **Do not restate code, list branches the type names already make clear, or explain a call by its signature.** No bold or capital emphasis, no stacked examples, no rhetorical build-up.
- Use `//` for implementation notes and `///` for documentation. Documentation blocks are 2–4 lines, not multi-paragraph essays.
- Files with an already-low comment density (roughly ≤15% of lines) need a light pass at most. Pure token docs, such as `/// 8pt`, are not narrative and should be left alone.

### Swift/SwiftUI Conventions

- Use SwiftUI for all UI unless a feature is only supported in AppKit (e.g., `NSPanel` for floating windows)
- **All user-facing copy is Simplified Chinese.** Every string the user reads or hears — panel labels, buttons, status text, the welcome message, the cursor's pointing bubbles, the spoken low-credits message — is written in Chinese directly in the source, not routed through a localization table. Product names and terms a Chinese developer would say in English (`Kiki`, `DeepSeek API Key`, `Control+Option`, model names like `Flash` / `V4 Pro`) stay in English.
- **What the user reads is said in Kiki's own voice, not the implementation's.** The task readout says the head is filling up (脑子用了 18% · 还有 82% 才满) rather than naming the threshold or the compression, because the number only means something to the user as something happening *to Kiki*. Identifiers, comments and this file keep the technical words; the split is by audience, not by concept.
- All UI state updates must be on `@MainActor`
- Use async/await for all asynchronous operations
- Comments should explain "why" not just "what", especially for non-obvious AppKit bridging
- AppKit `NSPanel`/`NSWindow` bridged into SwiftUI via `NSHostingView`
- All buttons must show a pointer cursor on hover
- For any interactive element, explicitly think through its hover behavior (cursor, visual feedback, and whether hover should communicate clickability)

### Do NOT

- Do not add features, refactor code, or make "improvements" beyond what was asked
- Do not add docstrings, comments, or type annotations to code you did not change
- Do not try to fix the known non-blocking warnings (Swift 6 concurrency, deprecated onChange)
- Do not delete logic on the grounds that the configuration it serves is not the one you are running — see "Rules That Bite If Broken"
- Do not rename `PRODUCT_NAME` away from `Kiki`, and do not rename `PRODUCT_BUNDLE_IDENTIFIER` away from `com.smarty.kiki` — the Keychain item holding the user's DeepSeek key is keyed on the identifier, so changing it orphans the stored key. The project directory and scheme being `kiki-desktop-agent` while the product is `Kiki` is deliberate, not a mismatch to tidy up
- Do not sign with an ad-hoc identity, and do not remove `ENABLE_DEBUG_DYLIB = NO` — see "Code Signing" for what it breaks
